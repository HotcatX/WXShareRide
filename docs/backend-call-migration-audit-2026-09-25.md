# 后端调用、成本与简化迁移审计

审计基线为提交 `88a9221`；2026-09-25 重构后，死代码已删除，当前调用文件名已同步更新。历史风险证据的行号指向该基线，不代表问题尚未修复。
审计日期：纽约时间 2026-09-25。源码基线：`88a9221`。范围为当前小程序、仓库内云函数、独立采集服务及公开统计服务；只读检查生产聚合数据，没有修改线上服务、数据库或客户端。网站外部代码库未纳入逐行审计。

## 结论

已经迁移的是公开统计读取和地点推荐两类路径，以及从一开始就直传服务器的新增行为采集。登录、行程列表/详情、发布/加入/退出、个人资料、模板、通知、二手/转租与图片仍大量依赖 CloudBase，不能宣称已迁移某个总调用百分比。

建议保留现有采集服务，另建一个模块清晰的业务单体，统一 API 和数据模型，逐域替换旧实现。重写的主要价值是消除重复事实、降低维护与一致性成本；仅凭调用费不能推导必须重写。

## 为什么现在算不出净节省

1. `utils/publicStatsClient.js:21` 的 HTTP/cloud/fallback 计数只在客户端进程内；首页诊断也是本地变量，没有集中上报。
2. `services/public-read-pilot/src/server.mjs:59` 记录的是同步 POST，GET 路径没有计数；Caddy 当前没有访问日志。等待更久不能补出已经没有记录的历史读取量。
3. `utils/rideDiagnostics.js:5` 只覆盖 9 个云函数，且要求已就绪的采集授权；每次前台最多 100 个成功和 20 个去重错误。它不覆盖所有市场、授权、直接数据库、云存储调用。现有 `service_request` 适合排错，不能当完整计费账单。
4. 新功能也增加了 CloudBase 工作：五分钟同步名义上 288 次函数执行/日，公开统计旧定时器转发到 `statistics` 名义上 48 次函数执行/日，合计约 336 次/日、10,080 次/30日。还有数据库轮询、每条事实写入及确认、身份授权。**这些是代码推导的执行量，不是已经核验的套餐扣量**，平台重试另计。

可以报告三组不同指标：

- 已迁移功能的直连比例 = 服务器成功直连 /（成功直连 + 对应 CloudBase 回退）；单独列失败与本地缓存。
- 同功能、同用户行为下的业务 API 迁移量：只计旧路径有对应调用的读取/操作；新增研究采集单列。
- 账单净变化 = 按 DAU、会话和有效业务动作归一化的迁移前 CloudBase 用量 − 迁移后实际用量，包含新增同步/授权开销。数据库、云函数、存储分别展示，以平台套餐明细做最终对账。

## 多久可以测算，以及应先补什么

先补持续计量，再开始观察窗口：

- 服务器按分钟持久聚合 route、method、status、请求数、时延直方图；不记录原始 URL 查询、IP、令牌和业务正文。区分健康检查/运维请求与客户端请求。
- 客户端通过统一调用层累计接口、版本、transport、成功/失败、fallback、缓存命中、重试数，复用现有 HTTPS 批量队列上传；不要为每次调用新增一次云写。明确后台退出丢失和本地上限导致的观测缺口。
- 每天取得 CloudBase 同时区的函数/数据库/存储用量与版本覆盖率；记录定时器和管理员测试的影响。缺少迁移前基线时，只给模型估计区间，不伪造严格因果节省率。
- 记录 TripActions pending 数、最老 pending 年龄和同步错误；接收端不能替代发送端积压指标。

时间建议是分析窗口而非自动承诺：

| 观察窗口 | 能给出的结论 |
| --- | --- |
| 当天、补齐计量后 | 各接口请求量和当前路由占比；仍不能推月账单 |
| 24–48 小时 | 日均调用初估、缓存/回退情况、早期成本范围 |
| 7 个完整自然日 | 覆盖一周课程和周末，对每 DAU/每业务动作的调用比较较有意义 |
| 14 天或更多 | 两个周周期及相近星期对比，估计更稳；仍受版本覆盖、学期/假期和流量变化影响 |

## 审计发现与优先级

以下是一致性与结构的静态审计发现，未用真实用户数据复现并发故障，也不声称线上已经发生。

| 优先级 | 发现与证据 | 后果与处理 |
| --- | --- | --- |
| P1 | `syncMyTripStatus/index.js:314` 读旧用户快照，`:377` 后整体覆盖 8 组行程数组 | 与加入/发布并发时可能把新关系覆盖，导致“我的行程”漏项。先改事务内重读或原子关系更新；目标模型以成员关系为唯一事实 |
| P1 | `createTrip/index.js:257`、`:297` 随机创建文档，无请求幂等键 | 请求已成功但响应丢失，再试可能重复发布。先加同用户+操作+requestId 唯一收据，返回原结果 |
| P1 | `tripManage/index.js:826` 查重、`:836` 新增评分、`:852` 更新聚合分离；`:755` 评分汇总读改写非事务 | 并发可能丢失聚合增量，失败可能留下部分完成状态；查重还需核验线上唯一索引。使用评分唯一约束与事务/可重建汇总 |
| P2 | 行程表关系、用户当前/历史数组、全局 role、统计汇总多处重复 | 每项业务需要修多份数据。角色属于某次参与关系，“历史”用时间与状态查询，统计明确为可重建派生值 |
| P2 | 客户端仍散落直接数据库/文件调用及重复资料查询 | 只替换云函数不能全迁移；先收敛到 API 层，合并可证明重复的请求，读路径按数据新鲜度缓存 |
| P2 | `statistics/businessOutbox.js:3` 每轮上限 10，`:7` 无效记录抛错 | 理论上限 120 事实/小时，异常头记录可阻塞队列。先补积压/失败指标，后按时间预算处理多批并隔离毒消息；当前接收负载未证明已满 |

不建议通过删除幂等、事务、身份验证、账号切换隔离、回访去重、版本/时间信息来“减少变量”。可删的是重复事实和过渡分支；研究复现及可靠写入需要的元数据应保留。

## 建议的新后端

部署形态：**Caddy + 一个 TypeScript/Node.js 业务应用 + PostgreSQL**，现有采集服务先保持独立；图片等放腾讯云 COS，应用只签发受限上传许可。先不引入微服务、Redis、Kafka 或 Kubernetes。2 核 2 GB 可作为受控的起步部署候选，是否承接全部峰值需压测后确定。

逻辑模块控制为账号、行程、地点与模板、市场、通知与反馈、统计与采集适配。模块是同一进程中的边界，不是六套服务。市场已有商品、转租、交易状态及网站管理接口，不能按“只有发布与加入”删掉。

核心关系：

- `users`：保留原 OpenID 关联，唯一范围为同一 AppID；资料、车辆信息按实际需要分组。全局司机/乘客字段最多作为 UI 偏好，不作行程权限依据。
- `rides`：保留供车/求车两类语义、容量、状态、版本、价格和时间；用明确类型和约束复用共有字段。
- `ride_members`：行程、用户、角色、所占座位/同行人数、参与状态及时间；替代用户里的 8 组关系数组。
- `ride_stops` / `places`：公共标准地点和用户本次具体地址分开；不把私人地址自动公开。
- `ride_templates`：星期、纽约本地时间、IANA 时区；具体行程用绝对时间。保留 DST 行为。
- `ratings`、`blocks`、`notifications`、`feedback`：各自唯一规则与授权边界。
- `listings`、`listing_media`、市场交易/发布者身份：保留网站发布者和微信身份的差异，避免伪造 OpenID。
- `idempotency_receipts`、`business_events`：业务写入与事实事件在同一事务提交；分析表按需重建，不把行为事件当订单事实。

认证使用 `wx.login` 的 code 由后端向微信换取可信 OpenID，再签发自己的会话。OpenID 是关联键，不能把客户端传来的 OpenID 当登录凭证；AppSecret 与 session_key 不下发。同一个小程序换后端无需更换用户 OpenID。[腾讯云开发团队的自建登录流程说明](https://tcb.cloud.tencent.com/blog/2026/06/08/wechat-miniprogram-ai-skill)

## 逐步迁移与退出 CloudBase

1. **量化并稳定现有系统**：补计量；先处理关系覆盖、发布幂等和评分事务。保留现有正式版可用性。
2. **收敛边界**：新建统一客户端 API 模块，替换页面直连数据库；优先地址/配置、重复 userInfo、通知计数等低风险请求，再依据实测流量排序列表/详情/市场。
3. **建立新业务库并影子验证**：全量导入与校验保留原记录 ID/OpenID、美国时区、历史价格语义；为旧写路径补齐可靠增量捕获。现有 TripActions 只覆盖部分行程事实，不能当整个系统 CDC。新读路径先做影子结果比较，不用于强一致座位/加入决策。
4. **按完整业务域切换单一写入方**：先账号/资料或低风险配置，再把整组行程发布、加入、退出、删除、状态变化一起切到新主库；不能按用户百分比让同一条共享行程分别写两个库。所有突变有幂等键，加入时校验/扣减座位与事件同事务。
5. **兼容旧客户端**：旧云函数可暂作认证与转发适配，但旧版仍直接写模板/通知等数据库，必须等版本覆盖足够，或安排最小维护窗口、收紧旧写入口并处理旧版提示。不能只把新包发出就关闭 CloudBase。
6. **图片、网站及后台任务迁移**：迁移云文件到 COS，维护旧 fileID→新资源映射；覆盖临时链接、头像、市场图片、清理任务、网站管理和公开预览等消费者。微信身份/必要平台接口仍调用微信，不应声称所有外部调用消失。
7. **最后退役过渡层**：旧云函数调用和直接 DB/Storage 调用已降至可解释范围，备份恢复演练通过，完成至少一周包含课程高峰的运行验证，才删除旧定时器、HMAC 转发和多余缓存分支；云端历史数据先保留只读。

读接口可保留故障回退。**写接口超时不得盲目换旧后端再执行**：超时可能只是响应丢失，新库已经提交；先用同一幂等键查询/重试当前写入方。真正切回旧库须先停写、补齐差异并核对版本，不能把“有 fallback”当作双主一致性的替代。

切流门槛应覆盖：新旧读结果/隐私字段一致、并发座位与重复点击测试、DST/周模板、旧版客户端、通知及回访、未知提交结果恢复、备份恢复、接口错误率与 p95 延迟、资源峰值与队列年龄。小样本采集成功不能代替这些业务验收。

## 成本口径与附录
