# 独立研究采集服务：托管选型与调用模型

核验日期：2026-09-22。本文是方案，不代表已部署、已开通付费或已测得真实访问量。仅核对官方文档，没有访问云账号用量或读取密钥。

## 建议

首选 **Cloudflare Workers Paid + D1 短期批次表 + R2 Standard 归档**。保留 CloudBase 的预约、成员权限、行程状态和问卷资格逻辑；新增独立 HTTPS 采集域名，小程序用 `wx.request` 批量直传。这样原始行为研究数据不经过 CloudBase，但独立平台仍有自己的调用、计算和存储成本。不要再通过现有 CloudBase 网站接口中转，否则并未卸载 CloudBase。

以目前假设量级，先维护一台 VPS 的收益主要在于 PostgreSQL 使用习惯、复杂 SQL 和自主运维；不能仅凭 CloudBase 套餐内 20 万次额度认定必须买服务器。托管方案的成本接近最低月费，后续仍能把标准 JSON 批次/归档移到 PostgreSQL。

## 两种最小方案

| 项目 | 自管小型 VPS | 推荐的 Cloudflare 方案 |
| --- | --- | --- |
| 接收器 | Node.js HTTP API，HTTPS 反向代理 | 一个 Worker，自定义 HTTPS 域名 |
| 热数据 | PostgreSQL 批次表，唯一键防重 | D1 批次表，唯一键防重 |
| 归档 | 定时脚本写压缩 JSONL/Parquet 到独立备份存储 | Cron 分块写 R2，分析时下载展开 |
| 初始账单预算 | 可先预留每月 US$10–20；这只是工程预算假设，非供应商报价，不含人工和所有备份成本 | Workers Paid 最低 US$5/月；D1、R2 在各自额度内无对应增量费；同账号其他业务共享额度 |
| 维护重点 | 系统补丁、数据库升级、备份恢复、磁盘增长、进程重启、TLS | schema、幂等、归档游标、限流、指标与费用告警 |
| 适合切换的条件 | 已有稳定运维服务器，或长期需要复杂 PostgreSQL 查询 | 当前小体量、美国东部用户、采集与离线研究为主 |

VPS 初期无需 Redis/Kafka 或常驻分析集群；同样采用持久化后再确认，不能只放内存队列。两种方案都需要一份独立可恢复备份和经过演练的恢复流程。

## 官方计费与限制

- **Workers**：付费最低 US$5/月，含 1,000 万入站请求/月、3,000 万 CPU 毫秒/月；超额分别 US$0.30/百万请求、US$0.02/百万 CPU 毫秒。免费档每天 10 万请求，但单次 CPU 限制 10ms，不能在未测量验签、校验和序列化成本前把它作为生产保证。[官方价格](https://developers.cloudflare.com/workers/platform/pricing/)
- **D1**：付费含每月 250 亿读行、5,000 万写行，以及 5GB 存储；超额每百万读行 US$0.001、每百万写行 US$1、每 GB-month US$0.75。免费是每日 500 万读行、10 万写行，总存储 5GB；超额可能拒绝查询。索引写入另外增加写行，数据库计费按行而非 HTTP 批次数。[官方价格](https://developers.cloudflare.com/d1/platform/pricing/)
- **D1 容量边界**：免费单库只有 500MB，付费单库 10GB；单行 2MB，单 SQL 最多 100 个绑定参数。单库串行执行查询，额度不是并发性能保证。设计单批不超过 64KiB，使用绑定参数，一批保存一行；不要把 50 个事件的全部字段拼为一个超参数上限 SQL。[官方限制](https://developers.cloudflare.com/d1/platform/limits/)
- **R2 Standard**：每月含 10GB-month 存储、100 万次 Class A、1,000 万次 Class B；超额存储 US$0.015/GB-month、A 操作 US$4.50/百万、B 操作 US$0.36/百万，无直接外网出流量费。写入和列举消耗 A，读取消耗 B，计费有单位进位；免费额度不适用于 Infrequent Access。[官方价格](https://developers.cloudflare.com/r2/pricing/)
- **R2 不能作为多人追加日志文件**：同 key 写入限制每秒 1 次；并发覆盖采用最后完成者获胜。采用唯一不可变分块，不让客户端直接改共享日文件。R2 操作具有强一致性，但 D1 与 R2 没有此设计可依赖的跨产品事务。[限制](https://developers.cloudflare.com/r2/platform/limits/)、[一致性](https://developers.cloudflare.com/r2/reference/consistency/)

## 可审计的调用和容量模型

以下全是情景假设：每次会话 30 条事件，合计 50KB 原始 JSON（包括较大的候选快照），每次会话恰好一次成功批传，每月 30 天。KB/GB 采用十进制。暂不计重试、令牌刷新、问卷、业务 outbox 导出、索引、备份、HTTP 头和压缩收益；会话不等于用户。

| 日会话 | 事件/日 | 逐事件上传/月 | 批传/月 | 原始数据/日 | 每月新增 | 365 天新增 | D1 留存 14 天原始载荷 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 3,000 | 90,000 | 3,000 | 5MB | 0.15GB | 1.825GB | 70MB |
| 500 | 15,000 | 450,000 | 15,000 | 25MB | 0.75GB | 9.125GB | 350MB |
| 2,000 | 60,000 | 1,800,000 | 60,000 | 100MB | 3GB | 36.5GB | 1.4GB |

这是纯客户端遥测；与先前另加 1MB/日核心事实的总量估算不同。30 条事件合一批将这部分请求减少 96.7%，不表示现有 CloudBase 47,700 次/日也能减少 96.7%。大批被大小上限拆开、重试、较早上传均会增加请求。

记日会话 S，平均批数 b，额外重试倍率 r，正常认证触发的令牌刷新数 T，则接收请求/月约 `30 × S × b × (1+r)`，另加 T、归档/撤回/运维访问。正常登录顺带签发令牌通常不增加 CloudBase 客户端请求，首次没有可复用登录或令牌过期时仍可能需要一次认证请求。

按最大发送情景 60,000 请求/月，**假设**平均 20ms CPU/请求，接收部分约 120 万 CPU ms/月，低于付费内含 3,000 万；20ms 是预算参数而非实测。一次批次写入一行不会变成 30 条事件写入；如果该表插入同时维护三个索引，初始入库可按约 4 次行写预算，即每月约 24 万次写行，归档状态、删除和撤回再另计。应以 D1 每次返回的 `rows_read/rows_written` 实测，不能宣称一次批传只算一次数据库操作。

假设热库总占用给原始载荷留 3 倍工程余量，最大情景 14 天约 4.2GB，接近 5GB 包含量，需要监控真实表/索引占用并及时归档；3 倍不是平台计费换算。长期全塞单库会撞上 10GB 边界，因此首版就实现归档，不为节省 US$5 而堆许多免费库。

R2 按参与者/日期组成有上限的不可变归档块（例如解压后最多 1–4MB），每块包含多个事件/批次；不逐事件写 R2。在三个情景中，即便每会话最终对应一次对象写也是每月 3,000/15,000/60,000 次，低于免费 A 额度，但推荐实际合并，且列举、重试、重写会另计。首月新增 0.15/0.75/3GB；这不是每月实际 GB-month，因为存量持续累积。最大情景到一年末若保存全部未压缩 36.5GB，再忽略当月增长差异，以该存量整月驻留粗算，超免费额度的存储费约 US$0.40/月（含进位）；备份和其他账号用量另计。

因此，单就这个研究采集负载，付费 Workers 可先按 **约 US$5/月基础费 + 实际超额资源**预算；不保证所有情景永久 US$5，也没有把域名、其他服务、税费和人工算为零。

## 最小可信数据路径

1. **客户端**：同账号本地有界队列；每批最多 50 条/64KiB。冻结 `batchId/eventIds/payloadHash`，持久化确认后才移除，失败退避，限制队列大小和保留期；`onHide` 只作尽力发送，不能保证退出前完成。直传独立域名不经过 CloudBase 代理。
2. **身份**：在现有可信登录返回中顺带签发仅用于研究的短期令牌，带 `iss/aud/sub/exp/kid/consentVersion`。采集 Worker 使用预置或缓存的公钥本地验签，固定允许算法；不每批调用 CloudBase。`sub` 为独立研究标识，不接纳客户端自行声明的 openid。验签只证明令牌，不能证明事件真实发生。撤回与参与版本在采集端持久保存并检查，不依赖令牌自然过期才停止收集。Workers 支持 Web Crypto。[官方接口](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/)
3. **接收与确认**：验证事件白名单、schema、大小和身份，记录服务端接收时间。D1 唯一键 `(subjectId,batchId)` 防重，同 ID 不同 hash 返回冲突。将批次和必要状态在同一次数据库事务提交后再 ACK；客户端 ACK 丢失的重试能得到相同确认。不能用 `waitUntil()` 后台落库、先向客户端谎报成功。D1 `batch()` 中任意语句失败会回滚该组。[官方批处理语义](https://developers.cloudflare.com/d1/worker-api/d1-database/)
4. **归档**：每天运行有界批次任务，持久保存清单和游标。选择已提交批次，写确定性不可变 R2 对象，校验成功后记录清单，再按热数据保留期删除 D1 载荷。中断可安全重放；D1 归档状态失败不能丢弃源数据。收件簿/去重摘要保留至少覆盖客户端最大重试期。限制每次任务处理量，不能假设一天全部压缩都可塞进一次执行。
5. **核心成功事实**：仍由原业务事务写 outbox，后台批量导出到独立服务，稳定事件 ID 幂等；失败可重试，成功 ACK 后推进游标。不能依赖客户端“我预约成功了”，也不能把预约成功依赖于跨云网络请求。原系统的 outbox 写、分页读、函数和外网出流量仍要计入 CloudBase。

本方案不引入 Queue 或 Durable Object 作为起步依赖；只有实测入库尖峰或归档执行限制构成问题时，再选择明确解决该问题的组件。

## 地区、删除和恢复

主要用户在纽约/新泽西，D1 创建时可使用 `enam`（北美东部）位置提示；提示不是固定地域或数据驻留保证。VPS 若选用，则优先测试美国东部到实际微信设备的链路。不能从套餐额度推导端到端延迟，必须真机验证冷启动、批传和恢复重试。[D1 数据位置](https://developers.cloudflare.com/d1/configuration/data-location/)

所有事件保留 UTC 时间与业务时区 `America/New_York`，对客户端时间保留可信度和服务端接收时间，不用固定 UTC-5 计算夏令时下的日频控。研究身份与业务身份映射独立、最小权限；日志不得输出 token 或完整研究载荷。

撤回必须同时阻止新批次、清理本地待上传队列、D1 热数据、R2 归档、分析导出和自管备份。按参与者分块有助于定位删除；归档任务在提交前检查撤回状态，避免撤回与导出竞态重新生成数据。备份设有限保留期，建立删除清单，恢复完成且重新开放查询前必须重放删除清单。D1 Paid 的 Time Travel 保留 30 天且默认启用，不能把删除活动库表述为即时消除所有历史副本；说明恢复历史的保留范围，限制恢复访问。[D1 恢复文档](https://developers.cloudflare.com/d1/reference/time-travel/)

## 验收与决策触发条件

- 先以合成数据验证：重复提交不增样本、同 ID 异内容拒绝、超大事件不阻塞后续批次、切账号不串数据、提交后 ACK 丢失可恢复、D1/R2 任一步失败不丢已确认数据。
- 试点分别记录 Worker 请求/CPU、D1 读写行/体积、R2 A/B 操作/存储、成功率/延迟、本地丢弃/重试和版本覆盖；不在每个事件中增加一个新监控请求。
- 价格内含量是资源预算，不是业务 SLO 或性能保证。基于真机与有界突发负载测试，再确定批量大小、频率和服务响应目标。
- 实测复杂查询需求、单库瓶颈、数据治理或既有 PostgreSQL 运维优势足够明确时再转 VPS；协议、标准导出和事件 ID 保持稳定，减少迁移成本。
