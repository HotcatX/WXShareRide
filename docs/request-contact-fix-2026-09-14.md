# 求车满员接单与联系方式修复

## 原因

- `requestDetail` 将所有非 `open` 状态视为已有司机，同时满员分支隐藏了司机接单按钮；后端 `acceptRequest` 也只接受 `open`。
- 接单后未清详情缓存，司机管理页允许使用最长 30 分钟的旧详情，导致仍以未接单身份隐藏乘客联系方式。
- 乘客查询失败被当作空名单；旧路线若 `passengerID` 漏记创建者，司机看不到发布者。
- 乘客侧缺失司机资料时，空对象阻止了兼容查询；历史微信字段别名也可能未展示。

## 修复约定

- 乘客人数上限为 4；`full` 表示乘客席位已满，与 `driverOpenid` 是否存在分别判断。仍在有效出发时间内的满员求车可以接一位司机。
- 人数包括发布者预订的同行席位，不能用账号数量覆盖。司机详情在两者不同时显示例如“4 人 · 1 位联系人”。
- 接单成功立即清详情缓存并进入司机联系页面，管理详情首次读取最新身份；旧的在途响应不能恢复失效缓存或覆盖新身份。
- `getTripDetail` 仅向当前接单司机返回 `passengerProfiles`，根据服务器可信 OPENID 校验，包含创建者及已加入账号，投影联系所需字段。游客、未接单司机和其他乘客拿不到该字段中的联系方式。
- 联系资料加载失败保留已知成员并提供重试；兼容 `wechatID`、`wechatId`、`wechat` 等历史字段。
- 加入、接单、退出和剔除以最新路线为准；保护满员重试、并发最后一席、司机退出后的容量状态、已取消及已过期路线。过期判断使用纽约时间，优先使用已保存的绝对时间戳。
- 新建求车校验 1–4 人及未来出发时间，状态由人数计算。

## 数据库事务

求车的路线修改和用户路线引用在同一事务内提交。用户资料先通过普通查询定位文档 ID，再在事务内读取和验证文档后修改；拉黑查询针对事务读取到的当前成员执行。

[CloudBase 官方事务文档](https://docs.cloudbase.net/en/database/transaction) 明确要求事务文档操作使用 `doc`，不支持 `where`。此前部分求车代码在事务内直接使用 `where`；本次按文档修正，但没有据此断言它是已证实的线上失败原因。

## 验证和上线

- 全量 436 项自动化测试通过，覆盖满员接单、重复加入、并发竞争、事务失败回滚、纽约时间、联系方式授权、旧请求覆盖以及历史资料兼容。
- 微信开发者工具远控使用仅针对测试路线 ID 的模拟云响应，实际点击司机接单并验证自动进入联系人页；另验证联系资料失败后点击重新加载恢复。模拟响应及缓存已还原，没有创建或加入真实路线。
- 真实云端详情接口执行只读检查，确认新字段存在，未接单访问者返回空联系人列表。
- `createTrip`、`joinTrip`、`tripManage`、`getTripDetail` 已增量部署成功；`joinTrip` 和 `tripManage` 各自包含 `requestState.js`。不新增云函数，不回填或删除业务数据。
- 后端部署与小程序发布分别生效：手机上的按钮、跳转及缓存修复需要发布包含这些改动的小程序版本。
