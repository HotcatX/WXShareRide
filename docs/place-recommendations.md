# 地点目录与推荐规则

按 2026-09-30 当前源码整理。静态配置由 PostgreSQL 业务 API 提供，动态地点、出行圈、选择票和榜单快照由独立采集服务维护。生产切换证据见[切库记录](backend-cutover-2026-09-30.md)，事件及研究解释见[采集数据合同](ride-research-data-contract.md)。

## 固定地点与参考价格

唯一维护源为 [config/locationCatalog.json](../config/locationCatalog.json)，包含地点 ID、别名、固定顺序、司机/乘客地址选项、城市树和参考报价。修改后按[地点配置说明](../services/backend/src/locations/README.md)运行同步脚本，生成后端、小程序和采集器的三个部署资产；不要直接修改生成文件。

`GET /api/v1/locations` 提供公共配置；客户端共享五分钟缓存。旧 CloudBase `Departure`、`Arrival`、`Departure_Request`、`Arrival_Request` 和 `Request_Price` 已迁入配置与归档，不再作为在线配置写入入口。

固定顺序以目录为准，当前为 Fort Lee、哥大、法拉盛、JFK、EWR、LGA、LIC、JSQ、Inwood、中城、NYU、Queens。顺序包含人工分组，不代表逐项按热度排名。`utils/placeCatalog.js` 统一解析名称与稳定 ID；改名和重排不批量改写历史行程原文。

机场具体接送点与机场地区分开处理。旧报价中“纽瓦克”可作为 EWR 的兼容键，但用户自由文本中的 Newark/纽瓦克不自动解释为机场；具体航站楼也不能直接套整个机场的报价。Fort Lee 历史报价键保留，未配置的报价不编造为 0。

## 客户端展示

自动区依次合并本账号最近最多 3 个自选地点、最多 8 个热门公共地点、最多 1 个新公共地点，并与固定区去重。本人最近记录按账号与城市隔离，展示近 90 天记录；服务不可用时仍可使用固定地点和本人最近地点。

[客户端推荐模块](../utils/placeRecommendations.js)通过已验证会话请求 `/v1/place-suggestions`，带城市、起终点侧、模式和另一端地点。成功结果缓存五分钟，合并在途请求；切号、授权范围、业务刷新标记和上下文变化隔离缓存。每次打开面板先展示缓存，再主动刷新；有效新结果在本次打开期间更新选项，保留当前搜索、自选草稿和已选值。面板关闭、账号或路线上下文改变后，迟到响应不再更新面板。

旧 `getTripList({action:'places'})` 返回空推荐，避免旧客户端继续扫描他人行程地址；新推荐请求只返回候选，不返回使用者身份。

## 地点如何进入公共候选

当前实现以[采集服务 places.mjs](../services/analytics-collector/src/places.mjs)为准：

- 来源是可信业务投递中的成功公开路线发布，或保留的 `legacy_snapshot`；草稿、个人资料和加入行程时的私人接送说明不作为新地点来源。
- 真实路线中，符合 `publicLabel` 文本过滤的未知地点可直接生成永久 `poi_...` ID，标记 `verification=published_route`。一次有效发布即可进入目录，不要求先有多个用户。
- 过滤排除房号/单元、联系方式、链接、占位文本及控制字符等模式。这是文本规则，**不等于经过外部 POI 或公共场所核验**；普通详细街道地址仍可能通过，不能声称所有自由文本都已确认公共性。
- 未自动接纳的文本按规则留在 `private` 或 `pending` 候选；服务端另有目录批准入口，要求归类和核验来源。合成事件不会创建或改名共享公共目录。
- 只有目录内、同城市、近 180 天存在公开使用记录的非固定地点参与动态推荐。新地点可见时间还受业务投递、目录规则及缓存影响。

最近 30 天批准的公共地点可进入新地点栏，每五分钟按确定性规则轮换一个；这是产品排序规则，不是随机实验。

## 出行圈

出行圈是本人成功业务参与形成的路线关系，不代表住址或已核实到达。按观察时点已知的成员状态与明确回访结果计算，事件必须已发生，计划服务日期窗口为观察日前后 90 天，因此可包含已发布的未来预约。

- 同城市内，两个不同标准地区组成无向路线对；正反方向属于同圈。
- 一次有效关联可形成临时圈；至少两个不同服务日，或正反两向均有记录时形成稳定圈。
- 退出、取消或当时最新明确回答“否”的参与记录不作为当前圈证据。主动关闭回访得到的默认 yes 不用于圈学习。
- 优先与当前另一端地点相交的圈，再按稳定性、近 30 天服务日数、窗口内服务日数和最近业务时间排序，最多取两个圈；相同结果按稳定 ID 排序。
- 机场端不连接两个社区。只含机场线路时，可用已知的非机场地区作偏好锚点，再回退同城市候选。
- `legacy_snapshot` 与新事务事实保留来源区别；迟到或乱序事件按观察时间和业务版本重建关系。

## 热门排序口径

确认选择票按 `账号 × placeId × 起终点侧 × 纽约自然日` 去重。展开、输入、曝光和网络重试不增加票数；原始有效行为事件仍保留，排序去重不等于删除研究记录。

同圈热门依次比较：近 30 天票数、近 30 天不同账号数、近 90 天票数、上一份榜单位置、稳定地点 ID；不足时以同城市候选补齐。多圈共享的票只计算一次，起点榜与终点榜分别生成。

当该城市和起终点侧已有非固定地点的有效选择票时使用 `confirmed_selection`；否则使用 `historical_usage`。历史业务使用按相同账号/地点/侧/纽约日单位去重，旧快照采用计划服务日作为使用时间；它不证明当时发生过一次选择。两种口径分别记录，不能直接相加或把旧使用量当选择量。

服务端保存 `snapshotId`、`catalogVersion`、`rankingVersion`、`preferenceVersion`、生成时间、圈和口径；客户端引用快照并记录实际显示次序、来源及缓存年龄。渲染、可见和明确选择是不同事件。

## 业务事实与研究边界

业务后端在 PostgreSQL 事务中写事件并冻结采集投影，由[投递任务](../services/backend/src/analytics/delivery.ts)按幂等事件 ID 发送并等待 ACK。active 进程正常情况下每十秒尝试投递，失败退避；这不保证每个新地点在十秒内展示，也不是旧 CloudBase 的五分钟同步计划。

圈、榜单和行为事件支持研究关联，但不能自动消除位置偏差。当前没有随机分配概率，也没有实际付款价、完整出行意向或全量成行结果；具体缺失与授权、保留规则见[采集数据合同](ride-research-data-contract.md)。
