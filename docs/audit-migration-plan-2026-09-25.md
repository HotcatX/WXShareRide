# 调用迁移计量与后台重整方案（2026-09-25）

审计基线为提交 `88a9221`；2026-09-25 重构后，死代码已删除，当前调用文件名已同步更新。历史风险证据的行号指向该基线，不代表问题尚未修复。
本文件基于仓库源码和已有部署记录进行只读审计；没有修改服务、云函数、数据库或小程序。本文件不把过去一次上线检查当作持续运行证据。正式版 5.0.6 已发布是本轮用户提供的事实；即时调用数与云账单应以本轮另行读取的运行数据为准。

## 结论

现阶段服务器承担了公开统计副本读取、研究事件批量入库和个性化地点推荐。**核心业务后台还在 CloudBase**。新增研究事件不是过去已有的云函数调用，不能用“收到多少条事件”解释为“省了多少次调用”。

建议用现有服务器逐步接管业务，建立一个按功能分模块的后台和一份业务权威数据源；保留 CloudBase 过渡，而不是一次搬空。先量出高频入口，再迁移读接口，最后按业务域切换写入。重写重点应是统一数据关系、时间和状态规则、服务调用入口，不是把变量批量改名。

### 迁移过渡本身也增加调用

- 采集授权的 `status`、首次 `activate`、会话到期刷新仍调用 CloudBase `statistics`。当前客户端每次进入前台重新查 status，只有未知账号首次另做 activate；服务器默认会话有效期 900 秒，上传前发现过期会刷新，不是每个事件调用一次云函数。
- 业务操作在原事务中增加 `TripActions` 台账；同步成功还逐条更新 ACK。这是可靠数据采集的成本，没有把原发布、加入事务从云端移走。
- 业务同步每 5 分钟执行一次：通常一天计划 288 次函数执行和 288 次待发查询，空队列也查询。重试、停机、配置变化另计。
- 公开统计目前保留旧定时函数转发到 `statistics`，按每小时一次估算为每天 48 次函数执行、24 次显式源数据读取。旧客户端走 `getPublicStats` 转发时也有包装层调用。

以上是**源码级执行/数据库操作估算，不是腾讯云最终计费次数**；平台的调用次数、数据库读写与函数执行资源需分别从用量明细对账。不能直接把它们相加当作同一个套餐指标。

## 2. 多久能测出来，怎样才算准确

**现在即可证明哪些请求走到了服务器；补齐下面的聚合计量后，24 小时可给第一份粗估，72 小时看趋势，至少一个完整教学周做较可信比较。** 哥大学生固定每周通勤，最好有上线前后一至两周同星期、相同时间段的基线。这个时间不是保证：某接口样本太少，就应继续积累，而不是满 7 天强行给百分比。当前缺少公开统计请求的持久化计数，单纯再等几天不能自动补出精确结果，也不能追回上线后已丢失的旧计数。

把三个问题分开回答：

1. **服务器承接量**：按接口统计成功请求、失败请求、重试、流量、批次、唯一事件。78 条事件装在 8 个批次里，就是 8 次成功批次上传和 78 条事件；不代表 78 次已避免的云调用。
2. **旧接口替代量**：真正成功从服务器返回的旧业务读操作数。公开统计的成功请求可作为旧读操作减少量的近似值，但需排除测试/监控，以及客户端已离页、丢包后回云等情况。
3. **净 CloudBase 降幅**：按同等访问量比较平台实际用量，扣除新版新增的授权桥、同步任务、兼容包装和台账写入。即使服务器请求增加很多，当前阶段净降幅也可能很小，甚至负数。

建议每天保存一行汇总：

| 指标组 | 必要字段 |
| --- | --- |
| 流量分母 | 日期和时区、客户端版本、活跃用户/会话、列表和详情访问、成功业务操作数 |
| 原业务调用 | endpoint/action、transport、attempt/result、缓存命中、fallback、耗时区间 |
| 扩展能力 | 研究批次、唯一事件、推荐请求及其旧路径替代范围、授权桥请求，独立列示 |
| 平台账单 | 函数调用、数据库读/写或平台对应口径、存储请求、流量、固定定时任务 |
| 稳定性 | 5xx/超时率、P95 延时、待发条数及最老记录年龄、磁盘/内存、版本覆盖率 |

比较式以“每 100 个活跃会话的调用数”及“每 100 次列表/详情访问的调用数”为主；业务写则按每 100 次成功发布/加入/退出归一化。另列总费用和请求绝对数。仅比较昨天和今天总量会把周末、上课日、用户增减混进迁移效果。

### 现有数据还不能精确反推总调用量

- `getPublicStatsPilotDiagnostics()` 的计数只存在当前客户端内存，源码没有将其集中上报。
- `rideDiagnostics` 只覆盖允许列表内的云函数；每个前台最多 100 次成功事件，错误会去重且最多 20 条。`statistics`、`marketApi`、直接数据库请求、存储请求不在这份完整计数中。
- 研究事件还受授权就绪、离线队列、容量、有效期和用户版本影响；研究批次表中的唯一入库批次不包含所有失败与重试请求。
- 当前 Caddyfile 没有配置访问日志；collector 的安全日志主要记录非预期异常，不能拿“无错误日志”当作“每个请求成功”的分母。

因此建议先增加低开销、持久化的**聚合计数**：服务器按 route/status 每分钟汇总；客户端把旧接口 transport/cache/fallback 的小计混入现有批次，避免为计量新增逐次 CloudBase 请求。平台用量单独按日留档。日志不需要记录完整 OpenID、正文或访问令牌；排障关联使用现有账号映射和请求 ID。

证据：[本地统计计数](../utils/publicStatsClient.js:24)、[诊断范围](../utils/rideDiagnostics.js:5)、[诊断限额](../utils/rideDiagnostics.js:90)、[Caddy 路由](../services/analytics-collector/Caddyfile:1)、[collector 日志](../services/analytics-collector/src/server.mjs:68)、[现有安全指标](../services/analytics-collector/src/metrics.mjs:1)。

## 3. 全迁移前必须解决的具体问题

### 3.1 研究台账不是完整业务副本

`businessLedger.snapshot()` 只保留限定数量的地点、参与者、状态、座位及参考价格等研究字段；备注、支付偏好、完整个人资料等业务字段不在快照里。它还会清理、截断字段，并把不认识的地点保留为空标识。因此当前服务器里的研究/成员历史不能直接提升为小程序业务主库。

真正迁库需要：全量导出和字段映射、稳定原 ID、完整业务增量或暂停写入窗口、按表计数与关键字段校验、删除标记、关系约束和最终对账。不能只把现有研究库“接给列表页”。证据：[业务快照](../cloudfunctions/createTrip/businessLedger.js:11)。

### 3.2 当前同步有明确的积压边界

`readPendingBusinessEvents()` 每次硬上限 10 条，五分钟一次，理想上限 120 条事实/小时，约 2,880 条/日；大报文、错误或超时会更少。选中的首批里有坏记录会整轮抛错，超大的队首记录也会阻塞。

短期先监控 pending 数量和最老年龄，再以有限轮数/时间预算排空，增加失败分类和隔离记录的可审计处理。不能为“同步快”在业务请求中同步等待服务器。该链路适合异步研究，**不适合座位库存实时副本**。证据：[批量上限](../cloudfunctions/statistics/businessOutbox.js:2)、[一轮只发一批](../cloudfunctions/statistics/placesSync.js:45)。

本轮主任务只读实测过去 24 小时服务器收到 151 条真实事务事实，分布在 79 个非空五分钟窗口；最大窗口为 5 条，没有窗口达到 10 条。已接收事件中最大延迟约 9 分钟。这个样本没有显示容量被打满，但服务器已收到的数据不能证明 CloudBase 待发队列为零；开发者工具登录过期，当前 pending 仍待直接核验。

### 3.3 旧版客户端直接写库不能靠云函数代理兜底

模板、个人资料引用、通知已读等存在直接数据库写入。旧包不会因为新服务器上线就改变行为。切换这些域之前必须发布统一 API 客户端并观察覆盖；仍活跃旧包要有明确过渡处理，不能突然收紧全部权限再认为已经兼容。

已通过云函数写入的域可以让旧函数变为可信兼容代理；**代理仍产生一次 CloudBase 调用**，只能逐渐消退。直接 DB 的旧调用不经过这个代理。证据：[模板写入](../pages/home/driverCarpoolTemplate/driverCarpoolTemplate.js:346)、[模板页写用户引用](../pages/home/CarpoolTemplateList/CarpoolTemplateList.js:343)、[通知已读](../pages/profile/notification/notification.js:129)。

### 3.4 写请求不能失败后无条件回旧后台

网络超时可能发生在服务器已经成功加入行程、但成功响应丢失之后。若再向 CloudBase 执行一次，会重复发布、重复加入或分裂库存。当前 `createTrip` 每次直接 `.add()`；研究台账的 `eventId` 只去重业务事实，不是创建请求的跨后台幂等键。

迁移后的每个业务命令应有 `Idempotency-Key`、请求摘要、结果记录，同一键和正文重试返回原结果，正文不同拒绝。所有请求路由到同一权威写库；不确定结果先查状态或重试同一端。对于座位共享的行程，所有用户的写操作必须落到同一处，不能按用户随机各写一半新旧数据库。证据：[当前创建事务](../cloudfunctions/createTrip/index.js:230)、[台账事件 ID](../cloudfunctions/createTrip/businessLedger.js:61)。

## 4. 建议的简单后台目标

建议单个 TypeScript/Node.js 应用按业务模块组织，统一验证、鉴权、错误格式和数据访问；同一个代码库与发布流程。模块可为账号、出行、地点与模板、通知/评价/拉黑、二手/转租、统计采集。后台任务放同一应用的 worker 入口，不引入微服务、Kafka、Redis 或 Kubernetes，除非测量出明确需要。

业务库建议评估 PostgreSQL：用事务、唯一约束和成员关系表承载发布、座位、加入和状态变化；现有 SQLite 采集库先维持运行，后续再决定是否合并存储。2 核 2G 足以开展旁路验证，但不能仅凭规格承诺全量业务容量。现有 compose 为 collector 设置 512 MiB、Caddy 与公开统计各 128 MiB 上限，并不代表实际一直占满；加入业务库后要实测内存、磁盘及并发，必要时再升 4G。

最值得减少的重复状态：

- `userInfo` 内多组当前/历史行程 ID 数组：改由成员关系表查询；历史记录由稳定事实与状态决定，用户表不维护另一套行程索引。
- 驾驶员发车/乘客求车共享参与者与状态规则：统一领域服务，保留不同需求属性；不能因想少几张表而抹掉求车发起人、接单司机的差别。
- `passengerCount` 的含义随类型不同：新字段明确区分总座位、已订座位、需求人数，金额统一整数 cents；显示文本留在边界转换层。
- 多种日期与本地字符串：业务时间存 UTC 时间点及服务时区；每周模板保留星期、当地时间、时区，再生成下一次发生日期，覆盖纽约夏令时。
- 多云函数复制的 ledger/catalog/状态规则：单一共享源，通过构建打包兼容函数，不再人工多点复制。
- 明确业务标识、请求幂等键、研究 eventId、会话令牌分别用于什么；用户仍以可信 OpenID 对应一个账号，不需要让页面传多个身份变量。

外部 HTTP 登录可通过微信登录 code 在服务端交换可信身份并签发自己的会话；迁移初期也可保留现有可信桥。OpenID 必须由可信服务端获取，不能把客户端提交的 OpenID 当登录凭证。不要在后台重写中顺带改变产品交互或增加采集按钮。

这些是建议目标，不是本次已实施的技术选型。具体实现开始前，应把接口/字段映射列全，尤其二手/转租、通知、文件、后台管理，避免只重写拼车后才发现仍依赖 CloudBase。

## 5. 分阶段切换与完成门槛

| 阶段 | 实施内容 | 切换门槛与回退 |
| --- | --- | --- |
| A：计量和止损 | 保存按日调用明细；统一接口清单；增加聚合指标、outbox 积压监控；确定各域权威库 | 连续完整日有可对账分母；没有盲目扩大线上切流 |
| B：统一访问层 | 新客户端统一 `api` 层；把直接 DB 调用移入 API；边界维持旧返回格式 | 同样功能回归通过，身份/访客/拉黑/分页/缓存不变；可切回旧读取 |
| C：迁移低风险读取 | 公开配置先行；高频列表/详情建完整副本、影子比对；副本只提供允许公开或当前身份有权读取字段 | 同一数据版本关键字段一致；无越权泄露；复制新鲜度和延时满足约定。过期时回权威源，预约仍由权威写库判断 |
| D：账号与业务写入 | 可靠会话；完整快照和增量；迁移成员关系；幂等命令；旧云函数兼容代理；按业务域统一权威写端 | 成员/座位/状态/金额对账零差异；重复、并发、超时后重试测试通过；旧客户端路径和后台任务已纳入 |
| E：文件与尾部功能 | 模板、通知、二手/转租、管理端、上传及文件历史链接；逐步移除桥接/兼容任务 | 观察至少完整教学周期，旧入口无有效业务流量，备份恢复演练通过；才退役旧函数/权限/计划任务 |

无需强制用户体验灰度入口。读取可先影子比对再按接口切流；写入的迁移单位是整个业务域或确定的行程归属，必须确保同一行程的新旧客户端都到同一个权威端。

### 建议的初始验收标准（实施时按实际量调整）

- 重复提交、丢失响应后的重试、并发抢最后一座，不新增重复行程、不超卖、不丢失已确认成员。
- 角色、成员、双向拉黑和私密联系字段权限测试全部通过；不把“公开读副本”扩大成公开用户资料库。
- 影子比对在同一个业务版本上检查关键字段，差异为零；不要把时间差造成的正常变化误判为不一致。
- 有实测峰值后，用代表性数据按至少该峰值的 2 倍压测；无 OOM/进程反复重启，错误率和 P95 不劣于当前可接受水平，预留内存与磁盘空间。具体 QPS 能力在测试后报告。
- 一次完整备份还原、一次写入后的回退演练，证明已确认写入不丢失。备份在同一台服务器本地目录不足以应对整机丢失，另做异机/对象存储加密备份。

### 回退方式需按切换阶段区分

- **读接口**：服务器故障回 CloudBase 权威读取，缓存/身份隔离保持不变，避免双方反复重试。
- **写权威尚未切换**：服务器只影子读取，直接关闭影子路径即可，不影响业务数据。
- **写权威已切换**：优先回滚应用版本并继续使用当前主库；如确需回到 CloudBase，先短暂冻结该域写入、将新提交反向补齐并对账、再整体恢复旧端。没有完成数据收敛前，不能用一个客户端 fallback 开关回旧库。

“业务调用全部迁出”与“CloudBase 调用数降到零”是两件事：旧版兼容、旧图片 URL、过渡身份桥、后台作业都有尾部流量。可以先让新增正式版业务调用完全走服务器，再决定是否仍值得保留 19.9 套餐；无需把套餐退役当作第一阶段目标。
