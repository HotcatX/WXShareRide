# 后端迁移映射审计：座位、城市与价格

本次仅只读分析私有导出 `data/backend-migration-20260925/{Carpool,CarpoolRequest,userInfo}.json`、聚合报告 `core-normalization-report.json`、当前导入器和可查的旧业务实现。没有修改原始数据、导入器、schema 或生产环境。本文只包含脱敏汇总，不包含行程 ID、OpenID、地址、联系方式或用户填写的原文。

## 口径与结论

导出含供车 3,733 条、求车 188 条、用户文档 1,166 条。导出完成时间为 **2026-09-26 02:08:46 UTC，即纽约 2026-09-25 22:08:46**；本审计固定以该时间为界，用 `latestDepartureAtMs` 判断是否未来。导出不是原子快照，不能将此处数量直接当作随后某时刻的在线状态。

| 分组 | 供车 | 求车 | 合计 |
| --- | ---: | ---: | ---: |
| 尚未到最后出发时间、未标记取消 | 22 | 1 | 23 |
| 已过最后出发时间、未标记取消 | 3,711 | 187 | 3,898 |
| 存量导出中显式取消/删除或无法判定时间 | 0 | 0 | 0 |

供车 `status=open` 实际有 23 条，其中 1 条在导出完成时已过出发时间，因此不能仅凭状态分组。旧取消逻辑会物理删除记录，存量没有取消行**不等于从未发生取消**。本表也不是已核实真人成行的数量。

核心判断：

- **596 条座位不平衡、227 条超过声明容量全部在历史供车中；227 条是 596 条的子集。** 三字段的数值矛盾可以复现，但不能据此断言历史实际超载、线上超卖或其具体成因。
- **2,802 条城市未映射全部是 `cityKey` 缺失**，不是发现了 2,802 个非法城市。缺失不允许直接默认纽约。
- **1,307 条价格拒绝中，528 条是可明确解析的旧美元写法，2 条明确免费，346 条没有明确金额；另有 431 条需要保留原文并人工/规则复核。** 不能把无金额参考文案当作坏数据，也不能从任意文字抽取第一个数字冒充价格。
- 23 条未来记录未出现这两类座位问题或城市缺失；其中 1 条求车使用内置参考价占位文案，应表达“价格未知”，不能填零。这仍不足以宣告整个迁移已安全。

## 座位：算式矛盾可证实，原始容量无法反推为事实

旧供车的真实写入规则是：创建时 `passengerCount` 与 `availSeatNum` 相同，前者表示声明载客容量；加入一个账号只令 `availSeatNum` 减一并追加一个乘客；退出/剔除反向处理，不应递减 `passengerCount`。当前代码和可查的 2026-06-20 版本都使用这套规则。

定义 `C=passengerCount`、`A=availSeatNum`、`N=passengers 中不同乘客账号数`。当前导入器检查 `A = C - N`，在这套语义下算式本身正确。

| 检查 | 未来供车 | 历史供车 | 与其他计数关系 |
| --- | ---: | ---: | --- |
| `A != C - N` | 0 | 596 | 本次主要异常集合 |
| `N > C` | 0 | 227 | 全部包含在上述 596 条中 |
| `C=0` | 0 | 57 | 全部包含在 596 条中；不是字符串转数值失败 |
| `A>C` | 0 | 149 | 属于同一类声明值不一致，不可与上行直接相加 |
| `A<0` | 0 | 0 | 没有负的剩余座位值 |

供车的 `passengerCount`、`availSeatNum` 全部为整数；4,973 个乘客条目均为对象。乘客账号没有重复、没有混入该行程创建者，也没有因找不到用户而被导入器丢弃。因此，**这 596 条并非首版导入器的类型转换、去重或身份映射误报**。但“声明容量”是否在早期版本被错误改写，不能仅凭快照确定。

596 条均满足 `A+N>C`，差值分布为：差 1 席 458 条，差 2 席 102 条，差 3 席 31 条，差 4 席 5 条。把 `C` 统一解释为“剩余座位”也不成立：只有 140 条满足 `C=A`，其余 456 条不满足。虽然全部行程的 `A+N` 都落在 1–8 范围，**这只说明可以构造一个自洽有效容量，不能证明它就是原始声明容量**。

时间上，596 条中 593 条创建于可查的最早相关 Git 版本（2026-06-20）之前；其余 3 条创建于 2026 年 8–9 月。594 条同时带有旧 `driverID` 且没有 `cityKey`，提示旧数据世代与异常有关，但不是因果证据。不能把当前代码假定为全部历史时期的实际部署实现。

求车需使用不同映射：容量固定 4；创建者原始同行人数为 `passengerCount - 非创建者乘客账号数`，额外加入账号每人一席。历史求车中有 40 条创建者占多席，不能按账号数量替代座位数。188 条求车在这项算式上未出现容量不足，但仍有一条创建者未列入 `passengerID`，以及聚合报告中的一条跨角色成员重复问题；这些身份异常仍须独立处理。

建议映射规则：

1. 正常供车保持 `seatCapacity=C`，保留原有乘客关系，每位乘客一席，司机零席；导入验证 `A=C-N`。不要创建一份新的可变剩余座位计数。
2. 596 条历史矛盾记录保留原始 `C/A/N` 证据及真实成员，不删除乘客、不截断人数、不修改源库。暂时隔离为待决历史数据；如未来采用 `A+N` 作为运营显示值，必须明确它是派生值，不能覆盖或冒充原始容量。
3. 57 条零容量无法直接满足当前 `seat_capacity BETWEEN 1 AND 8`。下一阶段应选择一种统一的历史不确定性保存方案并记录在 `SCHEMA.md`，再实现映射；不能临时补 1、补 4 或给每处增加不同别名绕过约束。
4. 未来记录切流前重新导出和核对成员/座位，必须处于一个权威写库。历史异常不能通过新客户端的自动写 fallback“修复”；读历史时可保留明确的旧库只读兼容路径，直到完整保存方案落实。

## 价格：金额、展示文案与未知值分开

首版 `parseListedPrice` 仅接受数字/数字字符串及非常严格的一种美元每人格式；其拒绝结果不能一律归因为源数据错误。

| 分类 | 供车 | 求车 | 合计 | 建议 |
| --- | ---: | ---: | ---: | --- |
| 首版已支持的数字/明确格式/缺值 | 2,596 | 18 | 2,614 | 保持现有精确转换 |
| 明确的旧美元前缀、后缀或币种文字 | 525 | 3 | 528 | 增加受控完整字符串匹配，转换整数分 |
| 明确免费 | 2 | 0 | 2 | 金额 0，保留原始含义 |
| 没有明确金额的文案 | 188 | 158 | 346 | 金额 `null`，保持展示含义，不能填 0 |
| 金额/单位/条件仍不明确 | 422 | 9 | 431 | 保留原文，继续规则/人工复核 |

新增可解析的 528 条美元写法进一步分为：美元符号后置 184 条，美元符号前置 41 条，明确美元币种文字后置 303 条。应通过完整匹配转分，不调用前端目前会“提取数字”的显示辅助函数来迁移资金含义；浮点乘 100 也应改为整数部分和两位小数拼接。

346 条无明确金额文案中，66 条与当前源代码中的内置参考价占位文案完全一致（65 条历史求车、1 条未来求车），2 条是可识别的协商类词，其余 278 条为没有数字的文本。它们可以明确表达“金额未知”，但展示文字不应凭空改成固定报价。431 条待决记录包含：9 条只有每人单位而无币种、331 条其他单数字文字、49 条附加条件的美元单数字文字、42 条包含多个数字。本文没有复制这些文字，多个数字也不自动认定为价格区间。

规范要求：`listedPriceCents` 永远是牌面价的可确认数值，不能称实际成交价。缺金额用 `null`；明确免费才用 0；复杂文字不能只抓首个数或求平均。如果目标 UI 需要完整保留历史价格展示，应在中央 schema 中一次性确定一个价格展示文本字段/结构，导入器和 API 使用同一名称；不要散落添加 `price/referencePrice/displayPrice` 等多套新别名。没有确认的币种、每人/整车单位及议价条件不可由转换器擅自补齐。

## 下一步实现与验收边界

本审计将“导入器过窄导致的拒绝”与“快照字段间真实不一致”分开，未证明每条历史数据的真实业务经过。聚合报告按问题计数，同一行可能命中多项，不能累加成坏行程数量。

下一步先为明确美元格式、无金额占位、已知城市别名与精确地点证据建立合成回归样例；历史容量和未决价格须先记录唯一保留方案，再调整导入器和 schema。所有原始导出继续私有保存，导入报告仍应在存在未解决问题时返回 `plan:null`。未来运营数据、历史证据与业务功能完整性均通过核验后，才可制定数据库单写切换；不得仅因本次 23 条未来记录通过局部检查就切流。
